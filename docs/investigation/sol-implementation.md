# PocketCli Investigation — núcleo

Estado em 27/10/2026: implementação parcial do RFC 01. O contrato `investigate.v1` e a projeção C.8 estão congelados. O comando já prepara planos, coleta metadados selecionados, preserva versões observadas, publica snapshots e oferece SQL local protegido. As lacunas abaixo aparecem como `coverage=unsupported|partial`, sem conclusão negativa inventada.

Changelog do contrato compartilhado: nenhuma alteração em relação ao apêndice C do RFC 01.

Segurança S09: a coleta rejeita uma resposta externa que ecoe a credencial usada na requisição (corpo literal, string JSON escapada ou header), antes de persistir cache ou evidência e antes de retornar dados ao Core. O recibo guarda apenas status e contagem de bytes; 401/403 continuam como `ERR_FORBIDDEN`. Um cache antigo que contenha essa credencial é descartado antes de ser reutilizado. Valide com `go test -buildvcs=false -run 'TestCredentialEchoCannotReachPersistentCacheOrCaller|TestLegacyCacheEchoIsDiscardedBeforeNetworkOrReuse|TestRequestReceiptPersistsEachRetryAndForbiddenWithoutBody' -count=1 ./internal/investigation/collect` (Go 1.22+, transporte falso e storage temporário; sem token real, rede ou variáveis de ambiente).

S03 blob Git: o cliente inspeciona também o conteúdo base64 declarado pela API antes de salvar a resposta HTTP em cache. Se o blob ecoar a credencial da fonte, a coleta do manifesto fica parcial e nem o corpo codificado nem o blob decodificado entram no storage; um cache antigo com esse conteúdo é descartado antes do reuso. Valide com `go test -buildvcs=false -run 'TestCredentialEchoCannotReachPersistentCacheOrCaller|TestLegacyBase64BlobCacheEchoIsDiscarded' -count=1 ./internal/investigation/collect` e `CGO_ENABLED=1 go test -buildvcs=false -tags investigate_sqlite -run TestBase64GitBlobEchoCannotEnterManifestStorage -count=1 ./internal/investigation/core` (Go 1.22+, compilador C/CGO para o segundo, transporte falso e storage temporário; sem tokens reais, rede ou variáveis de ambiente).

S03 reserva de quota: após resposta válida com headers de limite/remaining/reset, o cliente preserva por padrão os 20% finais da quota informada pelo GitHub ou Linear. A pausa usa segundos para o reset GitHub, milissegundos para Linear e o prazo mais longo entre as quotas Linear de requests, endpoint e complexidade. A resposta atual ainda é entregue; a próxima request espera ou retorna `ERR_RATE_LIMITED` antes da rede, inclusive após reiniciar o cliente. `POCKETCLI_INVESTIGATE_QUOTA_RESERVE_PERCENT=0..100` ajusta o limiar na CLI (`0` desabilita); valor ausente usa 20 e valor inválido aborta antes de abrir o storage. Sem limite/remaining válidos não há reserva inferida; se apenas o reset estiver ausente, a pausa conservadora é de um minuto. Valide com `go test -buildvcs=false -run 'TestReportedQuotaReservePausesNextClientBeforeNetwork|TestQuotaReserveUsesProviderResetUnitsAndConfigurableThreshold' -count=1 ./internal/investigation/collect` e `go test -buildvcs=false -run TestInvestigationQuotaReserveEnvironment -count=1 ./cmd/pocket` (Go 1.22+, storage temporário e transporte falso; sem tokens reais, rede ou outras variáveis de ambiente).

Versões de análise: o ruleset e o mapeamento publicado passaram a `1.12.0`. `R-DELIVERY-001` exige prova local de não ancestralidade; SHA apenas diferente deixa a checagem inconclusiva, evitando achado alto em uma revisão descendente normal. `R-DISABLE-001` agora usa somente a última observação operacional inequívoca do componente e ambiente dentro da janela; uma reativação posterior ou estados opostos no mesmo instante não geram achado de desativação. O import JSON rejeita nomes duplicados de componentes no mesmo ambiente antes de fixar a versão. O snapshot usa `rules.Version` diretamente, de modo que o relatório e `v_snapshot` mostrem a versão executada. O contrato `investigate.v1` permanece o mesmo. Valide com `go test -buildvcs=false -run TestDisableFindingUsesLatestUnambiguousObservationInWindow -count=1 ./internal/investigation/rules` e `CGO_ENABLED=1 go test -buildvcs=false -tags investigate_sqlite -run TestRuntimeImportIsTypedAndPinnedByPlan -count=1 ./internal/investigation/core` (Go 1.22+, compilador C/CGO para o segundo, storage temporário; sem tokens, rede, Chromium ou variáveis de ambiente).

Versão `1.13.0`: `R-LINK-001` só conclui “sem vínculo explícito localizado” para uma issue GitHub quando a coleta de issues, PRs e vínculos formais está completa no próprio repositório. Uma cobertura global completa de GitHub não é aplicada a issues Linear; o agregado `links` informa cobertura parcial quando há issues Linear porque a ausência de todos os vínculos formais ainda não é demonstrável. Repositórios GitHub completos continuam elegíveis mesmo que outro recurso esteja parcial. Valide com `go test -buildvcs=false -run 'TestMissingPRLinkRequiresCompleteCoverageOfIssuesOwnSourceAndRepository|TestMixedSourceLinksDoNotClaimCompleteWithoutLinearFormalCollector' -count=1 ./internal/investigation/rules ./internal/investigation/core` (Go 1.22+, storage temporário, sem token, rede, CGO, Chromium ou variáveis de ambiente). O fluxo offline com PDF real e o smoke autorizado em `irinery/socialMediaFactory` passaram novamente após a mudança, mantendo 25/26 páginas e reuso de 0 para 17. Snapshots já publicados mantêm o ruleset anterior; um novo run publica a versão nova. O contrato `investigate.v1` não mudou.

Ruleset `1.14.0` (mapeamento `1.14.0`): `R-REOPEN-001`, `R-EST-001` e `R-FLOW-001` só são publicados quando seus eventos comprobatórios estão dentro da janela confirmada; reabertura e estimativa exigem `evidence_id`. O fim da janela continua exclusivo. Valide com `go test -buildvcs=false -run 'TestEventFindingsRequireEvidenceInsideConfirmedWindow|TestDeterministicRulesAndUnknownCause' -count=1 ./internal/investigation/rules` (Go 1.22+, fixture em memória, sem token, rede, CGO, Chromium ou variáveis de ambiente). Snapshots antigos preservam seus achados e a versão anterior.

S05 dependências Compose: `depends_on` em lista ou mapa cria `depends_on` direto entre serviços declarados no mesmo manifesto, com evidência do blob Git verificado por OID. Uma referência a serviço ausente não vira vínculo e deixa `manifest_contents` parcial; nomes/chaves duplicados ou sintaxe inválida são rejeitados. Isso representa a dependência declarada de inicialização do Compose, sem afirmar tráfego, implantação ou causa. Valide com `go test -buildvcs=false -run 'TestParseManifestWithoutExecutingContent|TestComposeDependenciesRequireExplicitLocalService' -count=1 ./internal/investigation/core` e `CGO_ENABLED=1 go test -buildvcs=false -tags investigate_sqlite -run TestComposeDependenciesLinkOnlyVerifiedServices -count=1 ./internal/investigation/core` (Go 1.22+, compilador C/CGO apenas no segundo, GitHub falso e storage temporário; sem tokens reais, rede ou variáveis de ambiente).

S08 janela publicada: `Snapshot.WindowStart`, `Snapshot.WindowEnd` e `AnalysisReferenceAt` agora preservam, respectivamente, o início e o fim do plano confirmado. A projeção `v_snapshot` recebe os mesmos limites; snapshots já publicados continuam imutáveis e exigem novo run para obter essa correção. Valide com `CGO_ENABLED=1 go test -buildvcs=false -tags investigate_sqlite -run TestRunSnapshotAndVersionedObservation -count=1 ./internal/investigation/core` (Go 1.22+, compilador C/CGO, HTTP falso e storage temporário; sem credenciais reais, rede externa ou variáveis de ambiente).

Retry S08-04: uma exportação manual de PDF concluída pela CLI ou pela UI reconcilia o run em `report_failed` com o mesmo snapshot, sem nova coleta. O Core confere o número de achados antes de registrar `completed`/`completed_partial`; um PDF incompleto deixa o run pendente. Teste local específico: `CGO_ENABLED=1 go test -buildvcs=false -tags investigate_sqlite -run TestReportRetryClosesPartialRunWithoutRecollecting -count=1 ./internal/investigation/core` (Go, compilador C e SQLite CGO; não usa token, rede, Chromium nem Poppler).

Interrupção S08: `PauseRun` aceita `queued`, `collecting` e `building` como pausa retomável. Se a interrupção chega após publicar o snapshot, em `analysis_ready` ou `reporting`, o run vira `report_failed` e mantém snapshot/SQL para refazer somente o PDF. No terminal, `waitInvestigation` espera até 5 segundos pelo encerramento do worker antes de sair; o comando manual `report` passa SIGINT/SIGTERM ao contexto do renderizador. Em macOS/Linux/BSD, o Chromium é iniciado em grupo de processos próprio, encerrado inteiro quando o contexto é cancelado. Valide com `CGO_ENABLED=1 go test -buildvcs=false -tags investigate_sqlite -run 'TestPauseDuringPDFKeepsSnapshotReadyForReportRetry|TestCancelDuringCollectionDoesNotPublishSnapshot|TestReportRetryClosesPartialRunWithoutRecollecting' -count=1 ./internal/investigation/core` e `go test -buildvcs=false -run TestCancelledRendererStopsChildProcess -count=1 ./internal/investigation/report` (Go 1.22+, compilador C/CGO só no primeiro, `sh` POSIX no segundo, APIs falsas e diretórios temporários; sem tokens reais, rede externa, Chromium, Poppler ou variáveis de ambiente). Após a mudança, os gates `TestRealPDFWithFixture` e `TestOfflineRuntimeToPDF` também passaram com Chromium real e Poppler; o teste de grupo verifica um filho controlado do renderizador. O gate opt-in `POCKETCLI_CHROMIUM=/caminho/para/chromium go test -buildvcs=false -run TestRealChromiumCancellationLeavesNoWorkers -count=1 -v ./internal/investigation/report` inicia Chromium real com um perfil temporário, cancela seu contexto e confere com `ps` que não restam processos vivos no grupo (Go 1.22+, Chromium/Chrome e `ps`; sem token, rede externa, CGO ou Poppler). Passou neste Mac em 27/10/2026. O gate opt-in `POCKETCLI_CHROMIUM=/caminho/para/chromium CGO_ENABLED=1 go test -buildvcs=false -tags investigate_sqlite -run '^TestCLIReportSIGINTStopsRealChromium$' -count=1 -v ./cmd/pocket` compila a CLI, cria um snapshot operacional local e executa `investigate report` em outro processo. Um wrapper POSIX mantém Chromium real aberto até receber SIGINT; o teste espera o navegador iniciar, interrompe a CLI e confirma saída com `ERR_PDF_FAILED`, snapshot preservado, nenhum processo ativo do grupo e nenhum PDF temporário. Requer Go 1.22+, compilador C/CGO, Chromium/Chrome, `pdfinfo` e `ps`; não usa token ou rede externa. Passou neste Mac em 27/10/2026. O wrapper substitui apenas os argumentos de impressão para manter o navegador vivo durante o sinal; a geração do PDF real permanece coberta por `TestRealPDFWithFixture` e `TestOfflineRuntimeToPDF`.

O servidor local espera até cinco segundos pelas requisições em andamento após SIGINT/SIGTERM. A exportação iniciada no HTML usa um ciclo de vida do servidor, separado do contexto da requisição: fechar a aba ou perder a conexão não cancela o PDF. Ao encerrar, o servidor cancela os jobs restantes e espera sua limpeza antes de sair; o limite adicional de espera é cinco segundos. O mesmo encerramento bloqueia novos `StartRun`/`ResumeRun`, cancela os workers automáticos do Core, preserva o snapshot quando o PDF estava em curso e espera a liberação do lock antes de sair. Valide essa parte com `CGO_ENABLED=1 go test -buildvcs=false -tags investigate_sqlite -run TestStopActiveRunsCancelsAutomaticPDFBeforeExit -count=1 ./internal/investigation/core` (Go 1.22+, compilador C/CGO, storage temporário e Finalizer controlado; sem tokens, Chromium ou rede externa). O gate opt-in `POCKETCLI_CHROMIUM=/caminho/para/chromium CGO_ENABLED=1 go test -buildvcs=false -tags investigate_sqlite -run '^TestCLIServeSIGINTStopsAutomaticChromium$' -count=1 -v ./cmd/pocket` inicia a CLI `investigate serve`, desbloqueia a API local, inicia um run operacional offline, espera o Chromium real do PDF automático e envia SIGINT ao servidor. Confere que a CLI encerra, o navegador não sobrevive e o snapshot permanece em `report_failed`. O wrapper POSIX substitui os argumentos de impressão para manter Chromium vivo até o sinal; requer `pdfinfo`, `ps`, Go 1.22+ e compilador C/CGO, sem credenciais ou rede externa. Passou neste Mac em 27/10/2026. Valide com `go test -buildvcs=false -run 'TestInvestigationServerWaitsForActiveRequestBeforeExiting|TestInvestigationServerDeadlineCancelsActiveRequest' -count=1 ./cmd/pocket` e `go test -race -buildvcs=false -run TestReportJobOutlivesBrowserRequestAndStopsWithServer -count=1 ./internal/investigation/web` (Go 1.22+, loopback local e armazenamento temporário; o segundo comando usa compilador C para o detector de corridas; sem tokens, Chromium, Poppler ou rede externa).

## Build e testes locais

Fila de PDFs S08: a composição limita a tentativa inteira a 120 segundos, inclusive a espera por outra revisão em andamento. A espera pelo mutex local respeita o contexto; uma exportação cancelada não fica presa atrás de outro Chromium. Valide com `go test -race -buildvcs=false -run 'TestCancelledPDFDoesNotWaitForAnotherReportCacheJob|TestReportCacheFinalizesOncePerRevision' -count=1 ./cmd/pocket` (Go 1.22+, compilador C para o detector de corridas, storage temporário e Finalizer falso; sem token, rede, Chromium ou Poppler).

Pré-requisitos: Go 1.22 ou posterior, `gofmt`, compilador C para CGO, `git`, `sh`; para o PDF automático, Chromium/Google Chrome e `pdfinfo` (Poppler). Não são baixados durante a investigação. No macOS, se o navegador não estiver no `PATH`, configure `POCKETCLI_CHROMIUM` com o caminho absoluto do executável.

`pocket investigate doctor` verifica o motor SQLite e as dependências locais do PDF. Um `POCKETCLI_CHROMIUM` configurado para caminho inexistente ou não executável é informado antes da coleta. Valide com `go test -buildvcs=false -run TestInvestigationDoctorReportsInvalidChromiumBeforeCollection -count=1 ./cmd/pocket` (Go 1.22+, diretório temporário, sem credenciais, rede, Chromium ou Poppler).

gofmt -w cmd/pocket/investigate_command.go cmd/pocket/investigate_services.go internal/investigation/core internal/investigation/collect internal/investigation/gitmirror internal/investigation/storage internal/investigation/query internal/investigation/rules internal/investigation/secrets internal/investigation/web

O smoke Git real é opt-in e somente leitura: configure `POCKETCLI_INVESTIGATE_GITHUB_TOKEN` com uma credencial local com `Contents: read`, defina `POCKETCLI_INVESTIGATE_REAL_GIT_REPO=owner/repo` e execute `go test -buildvcs=false -run TestRealGitHistorySmoke -v ./internal/investigation/gitmirror`. Para observar o grafo de uma branch inventariada, execute `POCKETCLI_INVESTIGATE_REAL_GIT_REPO=owner/repo go test -buildvcs=false -run TestRealBranchGraphSmoke -v ./internal/investigation/gitmirror`; esse teste usa `POCKETCLI_INVESTIGATE_GITHUB_TOKEN` quando presente ou a conta ativa de `gh auth token`, sem imprimir a credencial. Ele usa orçamento estimado de 128 MiB pelo crescimento local do espelho e limita a execução a 3 minutos; não roda no CI sem essas variáveis. Em 26/10/2026, o smoke autorizado em um repositório privado concluiu o fetch, o diff local de 5 commits, a leitura de 5 entradas de árvore e o inventário de 42 branches em cerca de 2 s, com 748.122 bytes locais adicionais, 3.443 bytes de listagem e sem falha. O smoke novo em `irinery/socialMediaFactory` buscou o grafo de `refs/heads/Brandkit`, percorreu cinco commits e gastou 401.280 bytes locais adicionais mais 3.443 bytes de listagem, em cerca de 2 s.

Para validar a integração até o snapshot SQL, use as mesmas duas variáveis e execute `CGO_ENABLED=1 go test -buildvcs=false -tags investigate_sqlite -run TestRealCodeHistoryToSnapshot -count=1 -v ./internal/investigation/core`. O teste cria armazenamento temporário, restringe a coleta ao repositório escolhido e aos dois últimos dias UTC, seleciona issues GitHub, vínculos formais e histórico Git, limita cada sessão a 4 minutos, a transferência a 128 MiB e o armazenamento local a 256 MiB. Uma tentativa anterior no mesmo dia falhou com `ERR_AUDIT_FAILED: espelho Git corrompido` antes do PDF; a repetição passou. Essa corrida é uma causa plausível da falha intermitente, ainda sem reprodução instrumentada do caso real. Após a correção, o gate real passou novamente em 41 s, com as mesmas contagens e páginas. Não precisam de tokens, rede, Chromium nem `pdfinfo`; o teste de PDF real é opt-in via `POCKETCLI_CHROMIUM` e requer `pdfinfo`. A fixture SQL é `tests/investigation/core/demo.sql`. ## Uso atual

Use `POCKETCLI_INVESTIGATE_GITHUB_TOKEN` e `POCKETCLI_INVESTIGATE_LINEAR_KEY` somente quando a fonte correspondente estiver habilitada. No terminal interativo, a chave ausente é lida sem eco. Chaves nunca entram em flags ou YAML. O plano pode ser inspecionado antes de iniciar:

```sh
pocket investigate --scope ./auditoria.yaml --prepare --json
pocket investigate start PLAN_ID --confirm HASH
pocket investigate refresh INVESTIGATION_ID --prepare --json
pocket investigate serve INVESTIGATION_ID --snapshot SNAPSHOT_ID
pocket investigate report INVESTIGATION_ID --snapshot SNAPSHOT_ID
```

`pocket investigate serve INVESTIGATION_ID` abre a interface real. Sem `--snapshot`, seleciona o snapshot publicado mais recente; com a flag, usa exatamente o snapshot validado pela CLI. A tela Configurar permite importar YAML ou preencher escopo, fontes, credenciais de sessão, período e módulos; mostra recursos, janela, limites e hash antes da confirmação do run. O acompanhamento do run oferece pausa, retomada e cancelamento. Cobertura, mapa paginado com filtro, achados com filtros, SQL, comentários e revisões PDF usam o snapshot escolhido. A API desse servidor aceita apenas planos, runs, snapshots e registros da investigação indicada; IDs de outra investigação retornam `ERR_NOT_FOUND` antes de consultar SQL, gerar PDF ou chamar Claude. Consultas SQL livres recebem ID de execução, e uma consulta salva só pode usar uma execução do mesmo snapshot. O modo `investigate-preview` continua com a fixture separada. O teste `go test -buildvcs=false ./internal/investigation/web` valida IDs selecionados, desbloqueio e API local; não requer token, rede, Chromium nem variáveis de ambiente. Para testar só a fronteira entre duas investigações, execute `go test -buildvcs=false -run TestRealServerRejectsOtherInvestigationBeforeReadingOrWriting -count=1 ./internal/investigation/web` com Go 1.22+; não usa token, rede, Chromium, Poppler nem variáveis de ambiente. A sintaxe do script real também foi verificada com `node --check` (Node.js opcional, fora da suíte Go).

Para incluir um snapshot operacional, prepare primeiro um plano com `modules.runtime_import: true` e anote `investigation_id`. Importe o JSON local e prepare outro plano para a mesma investigação; o novo hash fixa exatamente a versão importada:

```sh
pocket investigate import-runtime INVESTIGATION_ID ./runtime.json
pocket investigate --scope ./auditoria.yaml --investigation INVESTIGATION_ID --prepare --json
```

Formato aceito (arquivo até 2 MiB, JSON UTF-8, sem campos extras ou chaves duplicadas):

```json
{
  "schema_version": "pocketcli.runtime.v1",
  "observed_at": "2026-01-08T00:00:00Z",
  "environment": "production",
  "components": [
    {
      "name": "api",
      "repository": "acme/api",
      "path": "services/api/go.mod",
      "enabled": true,
      "revision_sha": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
    }
  ]
}
```

`repository` e `path` são opcionais em conjunto; quando coincidem exatamente com um componente descoberto no Git, a observação é vinculada a ele. `digest` opcional aceita `sha256:` seguido de 64 caracteres hexadecimais. `enabled: false` registra desativação na data observada. O import não coleta hosts nem reconstrói estados anteriores.

S05-07: `enabled: true` sem `digest` nem `revision_sha` registra o serviço ativo, mas mantém `deployment_status=unknown` e não cria artefato de entrega. Um rótulo mutável como `latest` não identifica a revisão implantada. Com digest ou revisão declarada, a entrega recebe evidência do import e status `observed`, sem inferir causa ou vínculo temporal com PR. O teste integrado confere o status e a ausência de artefato na projeção SQL de um snapshot publicado. Valide com `CGO_ENABLED=1 go test -buildvcs=false -tags investigate_sqlite -run 'TestRuntimeImportIsTypedAndPinnedByPlan|TestUnversionedRuntimeStaysUnknownInPublishedSnapshot' -count=1 ./internal/investigation/core` (Go 1.22+, compilador C/CGO, storage temporário; sem token, rede ou Chromium).

Em TTY, `pocket investigate` abre o wizard: aceita YAML opcional ou nome, fontes, repositórios/teams, módulos e período em campos estruturados; `none` permite só `runtime_import`. Lista vazia em uma fonte habilitada descobre todos os recursos autorizados dessa fonte, mesmo quando a outra tem seleção explícita. Ele pede credenciais habilitadas sem eco, descobre recursos e mostra janela, módulos, limites, duração/custo a estimar, armazenamento, avisos e hash antes de iniciar. `--prepare` encerra após o resumo. ## Cobertura implementada e limites

O coletor faz descoberta limitada de repositórios GitHub e teams Linear; lê PRs, issues, comentários de issues/PRs, comentários de revisão, revisões formais e timeline GitHub, além de issues Linear inclusive arquivadas, com paginação. No Linear, introspecta `Issue` antes de consultar `history` e `comments` por issue; coleta transições de estado, estimativas e comentários. Até 100 issues por coleção são revalidadas em cada rodada, com cursor circular; campos ausentes no schema recebem `unsupported`. O inventário de projetos do team pagina inclusive arquivados, e associações explícitas de issue→projeto geram vínculos diretos. Revisões e timeline GitHub seguem o mesmo teto de 100 itens por coleção e rodada; o restante aparece como cobertura parcial. Os eventos observados de `ready_for_review` e `reopened` alimentam as regras de espera por revisão e reabertura. Um PR criado pronto sem evento `ready_for_review` não recebe horário ready inferido. A observação bruta fica em versões privadas por hash; títulos publicados recebem redação dos tokens da sessão. Páginas e cursores são confirmados em diário privado antes da próxima request; após interrupção, `resume` retoma do cursor confirmado. `SourceCursor` privado registra query/credencial, intervalos cobertos, watermark e checkpoint para PRs/issues/comentários GitHub e issues Linear. O watermark só avança em varredura confirmada; na ampliação de janela, issues Linear consultam apenas os intervalos antigos sem cobertura e o delta recente. GitHub ainda volta ao inventário completo quando falta cobertura anterior. O refresh dos dois tipos de comentário GitHub usa `since` por atualização com sobreposição de 48 horas; issues Linear usam `updatedAt` com a mesma sobreposição depois da primeira cobertura completa. Versões editadas ficam preservadas separadamente. Respostas ETag/304 reaproveitam representação por credencial e URL; corpos de até 256 KiB também persistem em 64 slots privados entre processos. Sem representação correspondente, o cliente faz requisição normal. Em 304, o orçamento contabiliza os bytes recebidos da rede, não o corpo reaproveitado. URLs e números de PR em issue, comentário ou corpo de PR geram relações diretas do tipo `mentions` quando o alvo coletado é inequívoco; a menção não é promovida a `references_pr`, e texto só parecido não gera vínculo. Refresh reaproveita versões idênticas apenas com a mesma credencial, recursos e módulos; uma janela histórica não recebe o estado atual de uma issue sem observação naquela janela. A paginação de PRs/issues GitHub pode parar na janela de reconciliação de 48 horas quando a coleta anterior foi completa e a janela não foi ampliada. Como essas listas não fornecem snapshot estável, qualquer varredura com mais de uma página fica `partial`; PRs/issues em delta também ficam `partial`, evitando declarar cobertura completa se itens mudarem entre páginas. Snapshots publicados não são alterados. O SQL consulta apenas a projeção SQLite C.8 por `snapshot_id`, com conexão somente leitura, authorizer, funções permitidas, limite de tempo/linhas/bytes e parâmetros bind.

Quando `code_history` está ativo, o Agent consulta a HEAD padrão e mantém um espelho Git privado de commits e árvores sem blobs (`--filter=blob:none`). O fetch usa URL sem credencial, configuração temporária isolada, hooks e helpers desabilitados, sem submódulos/LFS/GC automático. Versões antigas observadas continuam referenciadas localmente. `merge-base --is-ancestor` distingue avanço de divergência quando o grafo está completo; clone raso ou ancestral ausente fica `unknown`. A medição de bytes usa o crescimento/peak do espelho privado como aproximação conservadora da transferência, com cancelamento ao cruzar o limite. A observação de ref fica em journal por plano para que `resume` não perca uma divergência já detectada. A ref padrão é espelhada com grafo e árvores; as demais heads são inventariadas por `git ls-remote --heads --refs` e até três grafos de branches com OID novo são buscados por rodada, em fila circular persistida. A listagem tem teto de 10.000 refs e 1 MiB; respostas limitadas ficam parciais e não provam exclusão. Mudança de OID em branch não é classificada como rebase sem teste de ancestralidade. O journal fixa a lista e o estado anterior antes da projeção, de modo que `resume` reproduz criação, alteração e exclusão observadas. A árvore dessa versão é consultada via REST e identifica caminhos de `go.mod`, `package.json`, Dockerfile, Compose e OpenAPI. Blobs desses manifestos até 2 MiB são verificados pelo OID Git, guardados em cache privado e analisados sem execução. Compose gera componentes de service; árvores truncadas, blobs inacessíveis e parsers inválidos ficam parciais. Os arquivos alterados de PRs selecionados são paginados e ligados diretamente ao PR, em até 100 PRs por rodada; renames são eventos observados, sem inferir continuidade causal. O mapeamento arquivo→componente usa a árvore do próprio head do PR, obtida pelo commit fixado e guardada em cache por credencial. Até 20 heads distintos da ref atual são processados por rodada com cursor circular. O vínculo só é direto quando existe um único manifesto de diretório mais próximo naquela árvore; head inacessível, árvore truncada, manifesto ambíguo e fila pendente ficam parciais. Vínculos arquivo→componente dos heads antigos e suas evidências ficam preservados no refresh quando o PR permanece na janela, inclusive após force-push; não são remapeados para os manifestos do head novo. Os OIDs dos commits alcançáveis nas refs efetivamente buscadas são enumerados localmente; até 100 commits novos na janela viram eventos por rodada, e o refresh com o mesmo escopo continua a fila a partir dos eventos publicados. Um espelho antigo só de commits é atualizado com `git fetch --refetch --filter=blob:none` sob o orçamento configurado; se o Git local não oferecer `--refetch`, a cobertura de arquivos fica parcial. A seleção por data é separada do alcance; grafo raso e datas inválidas ficam parciais. Os arquivos dos commits alcançáveis são obtidos por diff local contra o primeiro pai, ou contra a árvore vazia no commit raiz; exclusões usam o manifesto da árvore do pai. Até 20 commits por rodada são mapeados por arquivo contra o manifesto inequívoco mais próximo na árvore da versão; o limite é de 3.000 arquivos por commit, 100.000 entradas e 1.000 manifestos por árvore. Renames não são inferidos do diff. O refresh preserva os vínculos anteriores e tenta novamente os commits com mapeamento parcial depois dos ainda não processados. `code_history` permanece parcial quando existe fila de branches/commits, listagem limitada, grafo raso, árvore ou manifesto inconclusivo. Git HTTPS, árvore e blobs requerem permissão `Contents read` no token selecionado.

Os commits de até 100 PRs selecionados por rodada são listados pelo endpoint de commits do PR, com paginação e journal próprios. Cada vínculo PR→commit registra a associação observada no horário da coleta; a data de autoria do commit não é usada como início presumido do vínculo. No refresh, a associação anterior só recebe fim de validade quando a lista está completa, cabe em uma página e o último SHA coincide com o head do PR coletado. Lista incompleta, com mais de 100 commits ou head inconsistente fica `partial` e não encerra vínculos anteriores. O teste `TestPRCommitMembershipClosesOnlyAfterCompleteRefresh` cobre avanço, remoção por force-push e lista parcial. A API real foi verificada de forma somente leitura em um PR autorizado: o último SHA da lista coincidiu com o head retornado para esse PR.

CI opcional coleta workflow runs do GitHub Actions e check runs nos heads dos PRs selecionados, com paginação e journal. Registra status/conclusão como eventos sem tratar sucesso de CI como implantação. Check runs exigem permissão `Checks: read` em tokens granulares; a cobertura é parcial quando algum head ou permissão não está disponível. A API de check runs por ref pode limitar resultados às 1000 check suites mais recentes, e o escopo não representa todo o histórico de CI. Deployments opcionais coletam registros e status; sucesso produz artefato com proveniência `declared` no nível do repositório. O estado efetivo do servidor e a associação com um componente de negócio continuam desconhecidos. Histórico de status anterior à retenção de 90 dias da API recebe cobertura parcial.

A fila de grafos não padrão requer refresh para esgotar os branches pendentes; ainda falta mapear arquivos que excedem os limites ou não têm manifesto inequívoco. `code_history` só passa a `complete` quando refs, branches, commits, arquivos e mapeamentos do escopo observado terminam; um coletor ausente ou parcial mantém o agregado parcial. O mapeamento de arquivos da ref atual fica completo quando todos os candidatos daquela ref têm manifesto inequívoco, inclusive quando não há candidatos; heads de PR diferentes são avaliados na coleção própria. A chave de idempotência é persistida antes do run; se o processo cair entre as duas gravações, repetir `StartRun` com a mesma chave recria o run com o ID reservado, sem duplicar execução. O dataset do build é persistido antes da projeção; a retomada reaproveita o mesmo snapshot e valida a projeção existente com hash privado e integridade SQLite, sem recoletar APIs ou substituir artefatos publicados divergentes. A recuperação reinicia runs interrompidos durante coleta/build como `paused`, reaproveita os diários GitHub, Linear e de observação Git e marca como `report_failed` a interrupção entre publicação do snapshot e fim do PDF, preservando o snapshot para nova exportação. Evidência JSON é normalizada na mesma representação persistida (inclusive escapes HTML) antes do hash; objeto local corrompido interrompe a coleta com erro de auditoria, sem sobrescrita silenciosa. A coleta das áreas ausentes permanece `unsupported`, `pending` ou `partial`. O mecanismo de regras cobre os oito IDs do RFC somente quando recebe os eventos e vínculos necessários. O espelho Git foi testado contra repositório local fictício e com fetch privado opt-in; o smoke da CLI descrito abaixo não ativou Git histórico nem Linear.
