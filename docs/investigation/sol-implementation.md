## Build e testes locais

Pré-requisitos: Go 1.22 ou posterior, `gofmt`, compilador C para CGO, `git`, `sh`; para o PDF automático, Chromium/Google Chrome e `pdfinfo` (Poppler). Não são baixados durante a investigação. No macOS, se o navegador não estiver no `PATH`, configure `POCKETCLI_CHROMIUM` com o caminho absoluto do executável.

```sh
gofmt -w cmd/pocket/investigate_command.go cmd/pocket/investigate_services.go internal/investigation/core internal/investigation/collect internal/investigation/gitmirror internal/investigation/storage internal/investigation/query internal/investigation/rules internal/investigation/secrets internal/investigation/web
go test -buildvcs=false ./internal/investigation/web
go test -buildvcs=false ./...
CGO_ENABLED=1 go test -buildvcs=false -tags investigate_sqlite ./...
CGO_ENABLED=1 go build -buildvcs=false -tags investigate_sqlite -o /tmp/pocket-go ./cmd/pocket
POCKETCLI_GO_BINARY=/tmp/pocket-go sh tests/run_smoke.sh
POCKETCLI_SHELL_SUITE_BUDGET=90 sh scripts/run_local_ci.sh
POCKETCLI_CHROMIUM=/caminho/para/chromium CGO_ENABLED=1 go test -buildvcs=false -tags investigate_sqlite -run TestRealPDFWithFixture -v ./internal/investigation/report
POCKETCLI_CHROMIUM=/caminho/para/chromium CGO_ENABLED=1 go test -buildvcs=false -tags investigate_sqlite -run TestOfflineRuntimeToPDF -v ./tests/investigation/core
```

O smoke Git real é opt-in e somente leitura: configure `POCKETCLI_INVESTIGATE_GITHUB_TOKEN` com uma credencial local com `Contents: read`, defina `POCKETCLI_INVESTIGATE_REAL_GIT_REPO=owner/repo` e execute `go test -buildvcs=false -run TestRealGitHistorySmoke -v ./internal/investigation/gitmirror`. Para observar o grafo de uma branch inventariada, execute `POCKETCLI_INVESTIGATE_REAL_GIT_REPO=owner/repo go test -buildvcs=false -run TestRealBranchGraphSmoke -v ./internal/investigation/gitmirror`; esse teste usa `POCKETCLI_INVESTIGATE_GITHUB_TOKEN` quando presente ou a conta ativa de `gh auth token`, sem imprimir a credencial. Ele usa orçamento estimado de 128 MiB pelo crescimento local do espelho e limita a execução a 3 minutos; não roda no CI sem essas variáveis. Em 26/10/2026, o smoke autorizado em um repositório privado concluiu o fetch, o diff local de 5 commits, a leitura de 5 entradas de árvore e o inventário de 42 branches em cerca de 2 s, com 748.122 bytes locais adicionais, 3.443 bytes de listagem e sem falha. O smoke novo em `irinery/socialMediaFactory` buscou o grafo de `refs/heads/Brandkit`, percorreu cinco commits e gastou 401.280 bytes locais adicionais mais 3.443 bytes de listagem, em cerca de 2 s.

Para validar a integração até o snapshot SQL, use as mesmas duas variáveis e execute `CGO_ENABLED=1 go test -buildvcs=false -tags investigate_sqlite -run TestRealCodeHistoryToSnapshot -v ./internal/investigation/core`. O teste cria armazenamento temporário, restringe a coleta ao repositório escolhido e aos dois últimos dias UTC, limita a sessão a 3 minutos, a transferência a 128 MiB e o armazenamento local a 256 MiB. Usa um Finalizer falso que percorre todas as páginas de registros; a renderização PDF real é verificada pelos testes opt-in abaixo. Em 26/10/2026, o smoke autorizado publicou snapshot consultável com 40 requests, 24.124.340 bytes contabilizados, 1.491 registros e 18 entradas de cobertura em cerca de 130 s, sem escrever no repositório remoto.

Os testes comuns de `internal/investigation/` usam APIs falsas e diretórios temporários. Não precisam de tokens, rede, Chromium nem `pdfinfo`; o teste de PDF real é opt-in via `POCKETCLI_CHROMIUM` e requer `pdfinfo`. A fixture SQL é `tests/investigation/core/demo.sql`. O build padrão sem tag mantém o Viewer e responde explicitamente que o motor completo não está disponível.

`-buildvcs=false` evita que o toolchain tente ler objetos Git ainda não hidratados pelo iCloud. O orçamento da suite shell é configurável por `POCKETCLI_SHELL_SUITE_BUDGET`; 90s é adequado para validação local neste Mac. O padrão do CI do projeto permanece inalterado.

## Uso atual

Use `POCKETCLI_INVESTIGATE_GITHUB_TOKEN` e `POCKETCLI_INVESTIGATE_LINEAR_KEY` somente quando a fonte correspondente estiver habilitada. No terminal interativo, a chave ausente é lida sem eco. Chaves nunca entram em flags ou YAML. O plano pode ser inspecionado antes de iniciar:

```sh
pocket investigate --scope ./auditoria.yaml --prepare --json
pocket investigate start PLAN_ID --confirm HASH
pocket investigate refresh INVESTIGATION_ID --prepare --json
pocket investigate serve INVESTIGATION_ID --snapshot SNAPSHOT_ID
pocket investigate report INVESTIGATION_ID --snapshot SNAPSHOT_ID
```

`pocket investigate serve INVESTIGATION_ID` abre a interface real. Sem `--snapshot`, seleciona o snapshot publicado mais recente; com a flag, usa exatamente o snapshot validado pela CLI. A tela Configurar permite importar YAML ou preencher escopo, fontes, credenciais de sessão, período e módulos; mostra recursos, janela, limites e hash antes da confirmação do run. O acompanhamento do run oferece pausa, retomada e cancelamento. Cobertura, mapa paginado com filtro, achados com filtros, SQL, comentários e revisões PDF usam o snapshot escolhido. A API desse servidor aceita apenas planos, runs, snapshots e registros da investigação indicada; IDs de outra investigação retornam `ERR_NOT_FOUND` antes de consultar SQL, gerar PDF ou chamar Claude. Consultas SQL livres recebem ID de execução, e uma consulta salva só pode usar uma execução do mesmo snapshot. O modo `investigate-preview` continua com a fixture separada. O teste `go test -buildvcs=false ./internal/investigation/web` valida IDs selecionados, desbloqueio e API local; não requer token, rede, Chromium nem variáveis de ambiente. Para testar só a fronteira entre duas investigações, execute `go test -buildvcs=false -run TestRealServerRejectsOtherInvestigationBeforeReadingOrWriting -count=1 ./internal/investigation/web` com Go 1.22+; não usa token, rede, Chromium, Poppler nem variáveis de ambiente. A sintaxe do script real também foi verificada com `node --check` (Node.js opcional, fora da suíte Go).

Para incluir um snapshot operacional, prepare primeiro um plano com `modules.runtime_import: true` e anote `investigation_id`. Importe o JSON local e prepare outro plano para a mesma investigação; o novo hash fixa exatamente a versão importada:

```sh
pocket investigate import-runtime INVESTIGATION_ID ./runtime.json
pocket investigate --scope ./auditoria.yaml --investigation INVESTIGATION_ID --prepare --json
```

Formato aceito (arquivo até 2 MiB, JSON UTF-8, sem campos extras ou chaves duplicadas):

```json
{
  "schema_version": "pocketcli.runtime.v1",
  "observed_at": "2026-01-08T00:00:00Z",
  "environment": "production",
  "components": [
    {
      "name": "api",
      "repository": "acme/api",
      "path": "services/api/go.mod",
      "enabled": true,
      "revision_sha": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
    }
  ]
}
```

`repository` e `path` são opcionais em conjunto; quando coincidem exatamente com um componente descoberto no Git, a observação é vinculada a ele. `digest` opcional aceita `sha256:` seguido de 64 caracteres hexadecimais. `enabled: false` registra desativação na data observada. O import não coleta hosts nem reconstrói estados anteriores.

Sem arquivo de escopo, use `pocket investigate --period 90d`; o padrão é descobrir recursos autorizados e exigir a confirmação do hash. Em modo sem TTY, omitir período ou confirmação retorna erro explícito. Para desabilitar uma fonte, use `--no-github` ou `--no-linear`. `--repo` e `--team` são repetíveis e limitam apenas a fonte correspondente; a outra fonte habilitada continua descoberta e exige credencial. O plano exibe avisos para módulos solicitados que ainda não têm coletor. A identidade das credenciais entra no hash do plano; mudar de conta exige preparar e confirmar outro plano, sem gravar o token. O armazenamento fica em `~/.local/share/pocketcli/investigations` com diretórios 0700 e arquivos 0600. O servidor escuta somente em loopback e exibe o código local de desbloqueio no stderr.

## Cobertura implementada e limites

O coletor faz descoberta limitada de repositórios GitHub e teams Linear; lê PRs, issues, comentários de issues/PRs, comentários de revisão, revisões formais e timeline GitHub, além de issues Linear inclusive arquivadas, com paginação. No Linear, introspecta `Issue` antes de consultar `history` e `comments` por issue; coleta transições de estado, estimativas e comentários. Até 100 issues por coleção são revalidadas em cada rodada, com cursor circular; campos ausentes no schema recebem `unsupported`. O inventário de projetos do team pagina inclusive arquivados, e associações explícitas de issue→projeto geram vínculos diretos. Revisões e timeline GitHub seguem o mesmo teto de 100 itens por coleção e rodada; o restante aparece como cobertura parcial. Os eventos observados de `ready_for_review` e `reopened` alimentam as regras de espera por revisão e reabertura. Um PR criado pronto sem evento `ready_for_review` não recebe horário ready inferido. A observação bruta fica em versões privadas por hash; títulos publicados recebem redação dos tokens da sessão. Páginas e cursores são confirmados em diário privado antes da próxima request; após interrupção, `resume` retoma do cursor confirmado. `SourceCursor` privado registra query/credencial, intervalos cobertos, watermark e checkpoint para PRs/issues/comentários GitHub e issues Linear. O watermark só avança em varredura confirmada; na ampliação de janela, issues Linear consultam apenas os intervalos antigos sem cobertura e o delta recente. GitHub ainda volta ao inventário completo quando falta cobertura anterior. O refresh dos dois tipos de comentário GitHub usa `since` por atualização com sobreposição de 48 horas; issues Linear usam `updatedAt` com a mesma sobreposição depois da primeira cobertura completa. Versões editadas ficam preservadas separadamente. Respostas ETag/304 reaproveitam representação em cache de memória por credencial e URL durante o processo; sem cache, o cliente faz nova requisição normal. Referências explícitas de issue ou comentário para PR coletado geram vínculos diretos; texto só parecido não gera vínculo. Refresh reaproveita versões idênticas apenas com a mesma credencial, recursos e módulos; uma janela histórica não recebe o estado atual de uma issue sem observação naquela janela. A paginação de PRs/issues GitHub pode parar na janela de reconciliação de 48 horas quando a coleta anterior foi completa e a janela não foi ampliada. Como essas listas não fornecem snapshot estável, qualquer varredura com mais de uma página fica `partial`; PRs/issues em delta também ficam `partial`, evitando declarar cobertura completa se itens mudarem entre páginas. Snapshots publicados não são alterados. O SQL consulta apenas a projeção SQLite C.8 por `snapshot_id`, com conexão somente leitura, authorizer, funções permitidas, limite de tempo/linhas/bytes e parâmetros bind.

Quando `code_history` está ativo, o Agent consulta a HEAD padrão e mantém um espelho Git privado de commits e árvores sem blobs (`--filter=blob:none`). O fetch usa URL sem credencial, configuração temporária isolada, hooks e helpers desabilitados, sem submódulos/LFS/GC automático. Versões antigas observadas continuam referenciadas localmente. `merge-base --is-ancestor` distingue avanço de divergência quando o grafo está completo; clone raso ou ancestral ausente fica `unknown`. A medição de bytes usa o crescimento/peak do espelho privado como aproximação conservadora da transferência, com cancelamento ao cruzar o limite. A observação de ref fica em journal por plano para que `resume` não perca uma divergência já detectada. A ref padrão é espelhada com grafo e árvores; as demais heads são inventariadas por `git ls-remote --heads --refs` e até três grafos de branches com OID novo são buscados por rodada, em fila circular persistida. A listagem tem teto de 10.000 refs e 1 MiB; respostas limitadas ficam parciais e não provam exclusão. Mudança de OID em branch não é classificada como rebase sem teste de ancestralidade. O journal fixa a lista e o estado anterior antes da projeção, de modo que `resume` reproduz criação, alteração e exclusão observadas. A árvore dessa versão é consultada via REST e identifica caminhos de `go.mod`, `package.json`, Dockerfile, Compose e OpenAPI. Blobs desses manifestos até 2 MiB são verificados pelo OID Git, guardados em cache privado e analisados sem execução. Compose gera componentes de service; árvores truncadas, blobs inacessíveis e parsers inválidos ficam parciais. Os arquivos alterados de PRs selecionados são paginados e ligados diretamente ao PR, em até 100 PRs por rodada; renames são eventos observados, sem inferir continuidade causal. O mapeamento arquivo→componente usa a árvore do próprio head do PR, obtida pelo commit fixado e guardada em cache por credencial. Até 20 heads distintos da ref atual são processados por rodada com cursor circular. O vínculo só é direto quando existe um único manifesto de diretório mais próximo naquela árvore; head inacessível, árvore truncada, manifesto ambíguo e fila pendente ficam parciais. Vínculos arquivo→componente dos heads antigos e suas evidências ficam preservados no refresh quando o PR permanece na janela, inclusive após force-push; não são remapeados para os manifestos do head novo. Os OIDs dos commits alcançáveis nas refs efetivamente buscadas são enumerados localmente; até 100 commits novos na janela viram eventos por rodada, e o refresh com o mesmo escopo continua a fila a partir dos eventos publicados. Um espelho antigo só de commits é atualizado com `git fetch --refetch --filter=blob:none` sob o orçamento configurado; se o Git local não oferecer `--refetch`, a cobertura de arquivos fica parcial. A seleção por data é separada do alcance; grafo raso e datas inválidas ficam parciais. Os arquivos dos commits alcançáveis são obtidos por diff local contra o primeiro pai, ou contra a árvore vazia no commit raiz; exclusões usam o manifesto da árvore do pai. Até 20 commits por rodada são mapeados por arquivo contra o manifesto inequívoco mais próximo na árvore da versão; o limite é de 3.000 arquivos por commit, 100.000 entradas e 1.000 manifestos por árvore. Renames não são inferidos do diff. O refresh preserva os vínculos anteriores e tenta novamente os commits com mapeamento parcial depois dos ainda não processados. `code_history` permanece parcial quando existe fila de branches/commits, listagem limitada, grafo raso, árvore ou manifesto inconclusivo. Git HTTPS, árvore e blobs requerem permissão `Contents read` no token selecionado.

Os commits de até 100 PRs selecionados por rodada são listados pelo endpoint de commits do PR, com paginação e journal próprios. Cada vínculo PR→commit registra a associação observada no horário da coleta; a data de autoria do commit não é usada como início presumido do vínculo. No refresh, a associação anterior só recebe fim de validade quando a lista está completa, cabe em uma página e o último SHA coincide com o head do PR coletado. Lista incompleta, com mais de 100 commits ou head inconsistente fica `partial` e não encerra vínculos anteriores. O teste `TestPRCommitMembershipClosesOnlyAfterCompleteRefresh` cobre avanço, remoção por force-push e lista parcial. A API real foi verificada de forma somente leitura em um PR autorizado: o último SHA da lista coincidiu com o head retornado para esse PR.

CI opcional coleta workflow runs do GitHub Actions e check runs nos heads dos PRs selecionados, com paginação e journal. Registra status/conclusão como eventos sem tratar sucesso de CI como implantação. Check runs exigem permissão `Checks: read` em tokens granulares; a cobertura é parcial quando algum head ou permissão não está disponível. A API de check runs por ref pode limitar resultados às 1000 check suites mais recentes, e o escopo não representa todo o histórico de CI. Deployments opcionais coletam registros e status; sucesso produz artefato com proveniência `declared` no nível do repositório. O estado efetivo do servidor e a associação com um componente de negócio continuam desconhecidos. Histórico de status anterior à retenção de 90 dias da API recebe cobertura parcial.

A fila de grafos não padrão requer refresh para esgotar os branches pendentes; ainda falta mapear arquivos que excedem os limites ou não têm manifesto inequívoco. `code_history` só passa a `complete` quando refs, branches, commits, arquivos e mapeamentos do escopo observado terminam; um coletor ausente ou parcial mantém o agregado parcial. O mapeamento de arquivos da ref atual fica completo quando todos os candidatos daquela ref têm manifesto inequívoco, inclusive quando não há candidatos; heads de PR diferentes são avaliados na coleção própria. A chave de idempotência é persistida antes do run; se o processo cair entre as duas gravações, repetir `StartRun` com a mesma chave recria o run com o ID reservado, sem duplicar execução. O dataset do build é persistido antes da projeção; a retomada reaproveita o mesmo snapshot e valida a projeção existente com hash privado e integridade SQLite, sem recoletar APIs ou substituir artefatos publicados divergentes. A recuperação reinicia runs interrompidos durante coleta/build como `paused`, reaproveita os diários GitHub, Linear e de observação Git e marca como `report_failed` a interrupção entre publicação do snapshot e fim do PDF, preservando o snapshot para nova exportação. Evidência JSON é normalizada na mesma representação persistida (inclusive escapes HTML) antes do hash; objeto local corrompido interrompe a coleta com erro de auditoria, sem sobrescrita silenciosa. A coleta das áreas ausentes permanece `unsupported`, `pending` ou `partial`. O mecanismo de regras cobre os oito IDs do RFC somente quando recebe os eventos e vínculos necessários. O espelho Git foi testado contra repositório local fictício e com fetch privado opt-in; o smoke da CLI descrito abaixo não ativou Git histórico nem Linear.

O `Finalizer` e o servidor da apresentação são injetados na composição CLI. A composição guarda uma chave por snapshot, anotações, redações aceitas e histórico de consultas para evitar gerar o mesmo PDF duas vezes. Se Chromium ou `pdfinfo` estiverem indisponíveis, o snapshot continua consultável e o run fica em `report_failed`; esse estado não satisfaz o DoD de PDF. Os testes opt-in geraram PDFs reais das fixtures offline com Chromium headless e Poppler, inclusive 237 achados paginados sem corte. Outro teste executa importação local → confirmação do plano → run → snapshot → SQL → PDF, sem chamadas externas. Um smoke autorizado e somente leitura com um repositório GitHub privado e janela de um dia publicou `completed_partial`, com 3 PRs consultáveis por SQL e PDF real de 5 páginas. A reexecução do mesmo plano reaproveitou os diários e fez zero requests externas. A lista de PRs permaneceu `partial` por paginação sem snapshot estável; comentários, reviews e timeline ficaram `complete`. O teste real identificou e corrigiu a perda de pacing entre `prepare` e `start`, o hash de JSON com caracteres HTML e a classificação de eventos de timeline não usados. Histórico Git real foi validado depois em smoke opt-in próprio; Linear e a matriz completa S09 ainda não foram validados em contas reais.
